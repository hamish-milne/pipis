# 22. The documentation kit is a Vite plugin, and the site is one app in two modes

**Decision.** `docs-kit/` is a Vite plugin (`docs-kit/vite.ts`) that knows Markdown, pages, navigation, the live examples' frames and the search, and nothing of the library being documented. A site gives it the app, as two entries, and what is particular to it (`site/vite-plugin.ts`); Vite does the rest.

- **The app is written once, as components, and runs on both sides.** `site/app.tsx` is the page: the header, the navigation, the article, the way to the next page, the contents. The server entry (`site/server.tsx`) exports `render(page, assets)`, which the build calls for each Markdown file and the development server calls for each request (`ssrLoadModule`), so a page is the same in both and a change is seen without a build. The browser entry (`site/client.ts`) is the page's script.
- **The two sides of the library are Vite environments.** The browser's build has the `pipis-hydrate` condition and the server's the `pipis-server` one (`resolve.conditions`, `ssr.resolve.conditions`), which is how the library is told which it is ([ADR 19](0019-server-rendering.md), [ADR 21](0021-hydration.md)). The demo apps are built and served by a Vite of their own (`app` in the options), because they are apps and must have the library as an app has it, which is not the build that the page's script has.
- **What only the server makes is a server module, and is a stub in the browser.** `site/docs.server.tsx` makes the navigation, the article (from the Markdown and the highlighter) and the contents, each inside a `Static`. The plugin replaces a module that the site names (`serverOnly.files`) with a stub that has the same names in the browser's build, and so what it imports (the Markdown reader, the highlighter, `node:fs`) is not in the browser's graph and not in what Vite scans. Its components take the page as a prop that the browser does not have, and the stub makes an empty `Static`, so the markers are the same. No data about the page is sent to the browser: the page's address in the site is the one thing it reads, from the element it takes over.
- **What does something is an island, in the page and in its text.** The theme switch, the menu, the search, the contents' follower, and in the article the code blocks, the live examples and the demos are islands (`site/islands.tsx` is the one list). An island with content that only the server makes (the highlighted code) is given it as a function prop, which the server calls and the browser does not have, and puts it in a `Slot` (`pipis/islands`): the server writes the content in a marker, and the browser, which makes the island again from its props, moves that marker into the island's own markup, so the code is not made again, does not flash, and what makes it is not in the script. In the hydrating build the same island is adopted in place instead.
- **Two choices, each a property.** `docsSite({ render, pages })` (`site/vite-plugin.ts`) is the site's configuration, and `vite.config.ts` says `{ render: 'hydrate', pages: 'separate' }`. `render` is how the browser makes the page live: `hydrate` takes over the page and then mounts the islands in its text, and `islands` mounts the islands only (`site/client.ts`). `islands` is a different build of the library as well: the page's script has the ordinary browser build, with nothing in it for adopting what a server wrote, and the islands are made in the browser from their props, replacing the server's markup. The components are the same, the page's own are not in the script, and the server writes no markers. The one difference in the markup is the frames of the examples and the demos, which an island that is made again makes itself, so there the server leaves them out (a reader with no script sees the code and not the running example). `pages` is how the Markdown is made into pages: `separate` (a page for each file) or `single`. A configuration is a file for `vp build --config` (`site/islands.config.ts`, `site/single.config.ts`, `site/single-islands.config.ts`).
- **A single page is the same pages on one.** The kit reads each Markdown file as before, with two changes that make it unique on a page: a heading is named for its page (`guide-lifecycle--mount`) and a link to another page is a link to that page's section (`#guide-lifecycle`, or `#guide-lifecycle--mount`). It renders once, from the index's model with the others in `merged`, in the order of the navigation and then of the files. The server's article makes a section for each, the navigation links to them, and an island marks the one being read (`aria-current`, as the page's own contents mark a heading). There is no pager and no contents, because a page's contents are not the page's any more, and no search index, because the find of the browser is the search; everything else is the same components, and both choices of `render` work with it.
- **The look is plain CSS, with two typefaces and no script.** `site/site.css` and `docs-kit/kit.css` are one design in variables (colour, radius, shadow, easing, and the icons, which are drawn as masks so they take the colour of their text), in a light and a dark theme. Inter and JetBrains Mono are self-hosted from the fontsource packages, as the latin subset only (about 88 KB, asked for early with `preload` and cached), with fallback faces that have their metrics so that the text does not move when they load. Motion is CSS and is off for a reader who asked for less: pages change by a cross-document view transition (the header and the navigation stay where they are), the theme changes by one from the page's script where the browser has them, the search opens with `@starting-style`, and the navigation on a narrow screen slides in. A block that has a `title` in its info string shows it above its code, and a page links to where it is written. The look is the site's, in `site/`, and the kit's own parts (code, examples, the search) are in `docs-kit/kit.css`, which uses what the site defines.
- **The front door and the foot.** The index of a site of separate pages is a home page (`site/landing.server.tsx`) and not the documentation's own index: no navigation, a headline and the first example running (an island, as in the documentation), the sizes that the size check holds (read from `tools/size-baseline.json`, so they cannot say what is not true), the reasons, the three ways to make a page live, and the documentation's sections. Its text is indexed by the search as every page's is. Every page has a foot (where the code is, and the company and year, which are read from `package.json` and `LICENSE`); the company's website is `url` in `companyOf`, which the foot links to when it is set. A single page has no front door: the documentation is the whole of it.
- **Files, or a server (`build`).** The third property is what the build leaves. `static` (the default) renders every page with the server's entry at build time and writes it, and the result is files and nothing else: the entry is built to do it (in `out/`, not in the output) because rendering with the built bundle is the production code, not a development transform of it. `server` writes the browser's files without the pages, and the server's entry, bundled with what it uses, beside `pages.json` (the pages as data), `assets.json` (the names of the scripts and style sheets) and `handler.js` (docs-kit/handler.ts with its types blanked out), a middleware `(request, response, next)` that renders a page when it is asked for with the same `render`. Express, Connect and `node:http` take it as it is (the recipe is in docs/authoring.md, with its two options, `base` and `sourceRoot`). The search index is built from the pages as files in either case, so a server's build renders them once into a scratch folder for Pagefind and keeps only the index. The development server is a server in the same sense, whichever is chosen.
- **The live example's frame is its own subsystem** (`docs-kit/frames.ts`): the example modules, the library as modules and an import map, so that the code a reader edits runs as the code the site built, in an iframe that is the only place it runs. The build writes these files and the development server serves them from memory.
- **The search index is Pagefind, run over the pages as written**, so a site of separate pages needs them as HTML, which is why `render` is two ways to make a prerendered site live. Not built: a client-only mode with no prerendered HTML, which is the Markdown reader in the browser's bundle, what `Static` and the server's modules avoid. The kit is meant to grow it as an option, with the components unchanged.

**Why.** A docs site is the place a framework shows how it is meant to be used, so the site should be an app and not a script that makes HTML: one description of the page, the parts that only read made where the Markdown is, the parts that do something next to the markup they make, and a build that is the toolchain's own. Vite's environments are the same split as the library's platforms, and its dev server gives the reload and the module graph for free; what it lacks (writing a page for each Markdown file) is one function.

**What it costs.** The page's script is 6.3 KB gzipped in hydrate mode and 4.4 KB in islands mode (`start/getting-started.html`), against 3.4 KB for the islands built by hand ([ADR 20](0020-islands.md)) and 1.4 KB for the original script. Hydrate mode has the hydrating build of the library (about 1.8 KB). What islands mode has over the hand-built islands is the components: the example now owns its whole figure (bar, frame with its height, code, editor), and the code blocks and the demos are islands too, where the old ones were a bar and a button that reached the rest of the page with the DOM. The editor (54 KB) and the search (1.8 KB) are loaded when used, as before. The site's source is longer than the islands version's, because the layout and the Markdown are in it now and not in the kit's string-making. In islands mode the saving over hydrate mode is the hydrating build and the page's own components; a site with a large reactive shell would save more.

**Evidence.**

- `site/site.test.ts` builds the site as `vp build` does and uses it in Chromium: every page is opened without an error or a warning (a warning is how a hydration says the page was not what the app makes) and every example is run in its frame; one is edited and reset; the search is used; the theme is switched; and a test fails if an element is added to the page or taken out of it while it hydrates. It checks the built page: that it is complete with no script, has the islands with the props that carry no code, links its script and style sheet, and that the script has none of the Markdown reader, the highlighter or `node:fs`.
- The same tests are run against the development server, which renders a page as it is asked for and serves the demo through its own Vite; and against the islands-only build, which has none of the page's components in its script and works the same.
- `src/pipis/islands.hydrate.test.tsx` and `tools/hydrate.test.ts` hold the library's side: an island is adopted, repaired and reported, a marker in a hydrated page is not mounted twice, and the markup that a server writes for a page with islands in static text is hydrated with nothing made again.
