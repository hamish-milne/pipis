# 21. Hydration is a platform, and adopts the server's nodes as they are mounted

**Decision.** A third platform, `platform.hydrate`, is chosen by the bundler's `pipis-hydrate` condition, as the server's is chosen by `pipis-server` ([ADR 19](0019-server-rendering.md)). It is the browser's platform plus what finds the nodes of a page that a server wrote, and `IS_HYDRATE` (with `IS_CLIENT`, and the new `IS_SERVER`) says which one the code is in; all three are constants, so what is for another platform is removed from a build. `hydrate(container, element, options?)` and `Static` are in `pipis/hydrate`.

- **Nodes are adopted when an element is mounted, not when it is made.** Elements are made inside out and mounted last to first, each with the node that follows it (`sibling`), so what an element wants is the node before `sibling`, or the last child of its parent. It takes the first node there that is its tag (a text node, a comment for a marker); nodes between that are in the way are removed; when there is none it is made, in place. After an element's children are mounted, the nodes of its that nothing took are removed. Attributes are not compared: the element is given its props, so the page is the one the app describes. A form control that has been changed since the page was written keeps what it was changed to.
- **The server writes what makes this simple.** With `renderToString(element, { hydratable: true })` every text node is preceded by `<!--t-->` (a browser joins text nodes that are next to each other, and drops an empty one), every region of `dynamic` (and so `If`, `OneOf`, `List`, `ReactiveList`, `Dynamic`) is written between `<!---->` and `<!--/-->`, and what `Helmet` wrote for the head is between `<!--h-->` and `<!--/h-->`. A region is found by its end marker (which is at `sibling`) and the start that matches it, and what is mounted inside it can only take nodes between the two. The markers are only in markup that is hydrated; a page that is not (a static site, or one with islands) is as before.
- **It is synchronous, and not re-entrant.** State may be written while the page is hydrated: a reactive is only a value, and a text or an attribute that follows it is given to a node that is already adopted, or is given by the element's own props anyway. What is refused is a region (`If`, `OneOf`, `List`, `ReactiveList`, `Dynamic`) that is already mounted changing what it shows, because that moves nodes under the search: it throws, to the error handling of what is mounted, naming the cause. A region's own first call and its own children are part of its mounting, so an `ErrorBoundary` can still show its fallback. `Effect`, `Watch`, `Portal` and a `ref` are held until the page is whole and then run, in order, under the error boundary they were mounted under; so the code in them sees the page as a browser would have made it. After that nothing is different from the browser's build, and a `dynamic` that is mounted later makes its nodes.
- **A mismatch is repaired, counted and said.** A missing node is made and an extra one is removed; the two are counted and reported to `onMismatch`, which is a `console.warn` by default. There is no further defence against a page that is very different: the repair is what makes the page the app's. If the app throws, the page is made again from nothing (a `try`/`catch` in `hydrate`), and the error is in the report.
- **Head tags are replaced.** The head is shared with the rest of the page and its elements are not in the tree, so what the server's `Helmet` wrote is removed when `hydrate` starts and the app's is made again.
- **`Static`.** `<Static>{() => content}</Static>` is a region whose server markup is adopted as it is, without calling its children. A page that has no use for what made it in the browser (a Markdown renderer) can leave that out of the browser's bundle.

**Why.** The alternatives were to do it in the elements' construction (the position is not known there), to make the hydrating code a mode of the browser's platform (every browser app would pay for it), or to hydrate by diffing the whole tree against the DOM (a lot of code for a case that is meant to match). Claiming at the mount, with a tally and a repair, is small, and a mismatch costs a few nodes and not the page.

The rule is placed where the harm is. A first version refused every write to a reactive while the page was hydrated; but the write is not the problem (a reactive is a value, and a binding to a text or an attribute is harmless), only a region that changes what it shows while its nodes are being found. So the check is on the regions' subscriptions (`subscribeWhileHydrating` in `dynamic.ts`), and nothing in `reactive.ts` or the storage adapters is involved.

**What it costs.** A build without the condition has none of it: the sizes in `tools/size-baseline.json` did not change. A counter app with an `If` is 1.46 KB gzipped in the browser's build and 2.78 KB in the hydrating one: about 1.3 KB for the finding of nodes, the hydrated element and `hydrate`.

**Evidence.**

- `src/pipis/hydrate.hydrate.test.tsx` (the `hydrate` project, jsdom): the nodes found are the nodes kept, attributes are given, missing and extra nodes are made and removed and counted, markers, regions and regions inside regions, a list's rows are in order and still update, a write as the page is mounted is allowed and one that changes a mounted region is refused, effects and refs wait, an error boundary, the head, form controls, `Static`, and a page that is made again.
- `tools/hydrate.test.ts` renders each of `tools/server.fixtures.tsx` and each live example of the documentation on the server, hydrates the markup in jsdom, and checks that the result is the page the browser makes, from the same nodes the server wrote, with no mismatch reported.
- `tools/deps.test.ts` keeps the platforms apart and the new seam (`hydrated`) the only way in; `tools/pack.test.ts` the condition in the package.
